# Слияние пар перехода для неначатых пакетов (этап 1)

Дата: 07.11.2026. Ответвление от `2026-11-05-wallets-design.md`: тот документ
запрещал трогать «Оплачено до перехода» и вводил `pricingAmount`. Здесь выбран
другой путь — ликвидировать особый случай, а не обслуживать его: неначатый
legacy-пакет получает свою сумму из парной денежной записи и дальше живёт как
обычный пакет.

## Задача

Дать менеджеру править неначатые пакеты без ограничений. Обычные продажи это
умеют уже сейчас; блокировка осталась только у legacy-пакетов уроков без счёта
(«Остаток на начало учёта пакетов», `paymentId = null`, `price = 0`,
`unitPrice > 0`). Локальная база: 113 неначатых таких пакетов на 113 кошельках.

## Правила

**Покрытие.** «Свои» деньги неначатого пакета — `remaining × unitPrice` (все
уроки ещё не потрачены, их деньги целиком лежат авансом). Эта сумма
перекладывается из денежных записей кошелька в `price` пакета.

**Источник денег.** Денежные записи перехода на том же кошельке
(`paymentId = null`, `lessonCount = 0`, `price > 0`, ACTIVE), draining в
порядке `(date, id)` — сначала самые ранние. Пакеты на кошельке обрабатываются
в том же порядке `(date, id)`. Запись может быть опустошена частично; остаток
на ней — деньги уже потраченных уроков — остаётся.

**Непокрытые — вручную.** Если денег на кошельке не хватает (23 кошелька из
113), пакет пропускается целиком (ничего не меняем) и попадает в итоговый
список для ручного разбора. Частичной перекладки нет: полупустой `price` у
пакета хуже отсутствия правки.

**Дата денег.** «Авансы» режут поступления по `createdAt`; денежные записи
задатированы днём первого занятия, пакеты уроков — днём бэкфилла (30.08.2026).
Чтобы перекладка не двигала авансы задним числом, пакету уроков выставляется
`createdAt` самой ранней опустошённой записи. Поле `date` (очередь списания)
не меняется.

**Инварианты.** Уроки и журнал не двигаются вовсе: `lessonsBalance`,
`totalLessons`, `totalPayments`, выручка, посещения — без изменений. Сумма
`Σ Package.price` по кошельку сохраняется, поэтому «Авансы» и «Прибыль»
видят ноль изменений. Скрипт идемпотентен: обрабатываются только пакеты с
`price = 0`, после прогона их не остаётся.

## Правка после слияния

У слившегося пакета есть `price`, но нет счёта. `planPackageCorrection`
ослабляется: блок «перенесён из старой системы» снимается для пакетов без
счёта с ненулевой суммой — они правятся как обычные (пересчёт
`unitPrice = floor(price / lessonCount)`, прошлых занятий нет, счёта нет —
шаг обновления `Payment` пропускается). Подарки отличаем по событию выдачи
`LESSONS_GIFTED` (как предписывает дизайн 05.11), им сумма по-прежнему
заблокирована. Пакеты с `unitPrice > 0` и `price = 0` (23 непокрытых) остаются
под прежним запретом.

## Что НЕ входит

- 44 начатых legacy-пакета — следующий этап (та же формула перекладывает
  только `remaining × unitPrice`; потраченное остаётся на денежной записи и
  гасится признанной выручкой).
- Ручной разбор 23 непокрытых кошельков — только список.
- Прогон на проде: скрипт сначала на локальной копии, прод — отдельной
  процедурой по `docs/prod-migration.md`.

## Реализация

Разовый скрипт `apps/platform/scripts/merge-legacy-unstarted-pairs.ts` в
традиции `backfill-*`: по умолчанию сводка вхолостую (сколько пакетов сольётся,
на какие суммы, список непокрытых с кошельками и недостачей), `--apply`
пишет. Изменение `planPackageCorrection` и `readCorrectionFactsTx`
(признак подарка) — продуктовый код с проверкой сверками `check-ledger`,
`check-wallet-balance`, `check-package-statuses` до и после.
