# Кошельки: анализ и проект изменений

Дата: 05.11.2026. Основание: код текущей ветки и локальная PostgreSQL `localhost:5432/alg`. Это проверка локальной копии, не утверждение о состоянии прода. Продуктовый код и данные не изменялись.

## Задача и согласованные правила

Школа должна самостоятельно исправлять привязку занятий и фактический остаток после сверки с внешним учётом.

- Привязка принадлежит записи **ученик — группа**, а не группе целиком. Кошелёк одного ученика может обслуживать несколько групп.
- При перепривязке менеджер выбирает: сохранить оплаченные занятия или пересчитать историю из нового кошелька.
- При коррекции количества пересчитывается цена **всех** занятий выбранного пакета, включая прошлые. Влияние на отчёты показывается до сохранения, но само по себе не запрещает исправление.
- Вводимый остаток устанавливается **до** погашения занятий, ожидающих оплаты. Например, при вводе 7 и двух ожидающих занятиях итог кошелька может быть 5.
- Для старых пакетов без счёта **менеджер сам указывает расчётную стоимость**. Не вычислять её автоматически из старой цены урока. Поступления и отдельные денежные записи перехода не меняются.
- Архивные кошельки полностью исчезают из пользовательского интерфейса, без «Показать архив». История финансов и сами записи в БД сохраняются.

Предложения автора, требующие проверки при чтении: основной ввод — остаток выбранного пакета, рядом общий остаток кошелька; режим перепривязки по умолчанию сохраняет оплаченные занятия; архивировать можно только кошелёк без операционных обязательств. Внедрение не входит в этот этап.

## Что работает сейчас

| Узел                           | Ответственность и связь                                                                                                                     |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `StudentGroup.walletId`        | Текущий кошелёк конкретного ученика в группе. Истории назначения нет.                                                                       |
| `Payment`                      | Сумма поступления/счёта, статус, метод, внешний id CRM. Один счёт может обслуживать пакеты нескольких детей.                                |
| `Package`                      | Права на занятия: размер, остаток, цена пакета, цена урока, дата очереди, кошелёк. Пакеты без счёта допустимы.                              |
| `Attendance`                   | Фактическое списание: `packageId`, `price`, `amount=1`. `price=null` означает отсутствие оценки; бесплатное проведённое пробное получает 0. |
| `WalletEntry`                  | Журнал движений уроков. Откат — новая встречная запись, а не изменение старой.                                                              |
| `Wallet.lessonsBalance`        | Кеш суммы движений, равный сумме остатков активных пакетов.                                                                                 |
| `StudentLessonsBalanceHistory` | История для человека: автор, причина, до/после, дополнительные сведения.                                                                    |

Оплата через `payments/create.server.ts` создаёт счёт и пакет; подтверждение вызывает `activatePackageTx`. Выданные уроки закрывают ожидающие занятия. Списание в `ledger.server.ts` выбирает первый активный пакет с остатком по `(date, id)`, уменьшает пакет и кошелёк, записывает цену в посещение и движение в журнал. Без пакета занятие остаётся ждать оплаты; баланс не становится отрицательным.

Кошелёк определяется сначала по `Attendance.walletId`; бесплатное пробное не наследует кошелёк группы. Для отработки используется группа исходного пропуска. Возврат следует за фактическим пакетом, в том числе после его переноса. Старые долги и отменённые пакеты требуют специальных встречных движений; их нельзя массово пересписывать как обычные занятия.

`transfer.server.ts` переносит **пакеты целиком**, вместе с непотраченным остатком, парой `TRANSFER`. Исторические цены при переносе пакета сохраняются. Перенос между учениками и в архив запрещён. Перепривязка `relinkGroupTx` уже существует, но UI скрывает её константой `RELINK_ENABLED=false`. Она возвращает списания группы и заново гасит их из нового кошелька; вместе с этим могут погаситься ожидающие занятия других групп. Совместная операция сначала переносит пакеты, затем группы.

`correction.server.ts` и чистая функция `correction.ts` уже исправляют количество/сумму пакета. Новая цена — `floor(price / lessonCount)`; прошлые занятия переоцениваются через `REVERSAL + CHARGE`. CRM запрещает менять сумму, но не количество. Старые пакеты без счёта с ненулевой ценой урока или суммой запрещены полностью. Подарки реализованы отдельными нулевыми пакетами, но скрыты в UI; включать их в рамках этой задачи не требуется.

`getStudentWallets` уже возвращает только активные кошельки для селекторов. Карточка ученика получает все кошельки через `getStudentDetail` и отображает их все. Кабинет родителя показывает архив в блоке «Завершённые курсы». Архивация сейчас не проверяет остаток или группы; списание по существующей связи не проверяет статус кошелька. Поэтому архив фактически не означает прекращение операций.

## Отчёты и сверки

- «Выручка» читает цены посещений через `revenue/compute.server.ts`.
- «Прибыль» и «Авансы» используют `chargeable.server.ts`; авансы сопоставляют стоимость активных пакетов с признанной выручкой. `Wallet.totalPayments` — старый счётчик, не источник денег для этих отчётов.
- Исправление суммы обычного пакета меняет счёт на разницу, поэтому затрагивает и поступления/эквайринг. Переоценка занятий меняет прошлую выручку и зависящие от неё показатели. У «Авансов» поступления сейчас режутся по `createdAt`, а не `Package.date`; смену этого правила выделить отдельно, не включать незаметно в рефакторинг.
- `check-ledger.ts`: журнал против кошельков, пакетов и выручки посещений, парность откатов, отрицательные остатки. Для `PENDING` равенство журнала и `remaining` не требуется: уроки ещё не выданы.
- `check-wallet-balance.ts`: остатки активных пакетов против кошельков. Дополнительная диагностика `lessonCount − Σ attendance.amount − remaining` не является блокирующим assert и не учитывает все исторические операции.
- `check-package-statuses.ts`: согласованность выдачи пакетов и статусов счетов, пустой журнал черновиков, нулевой остаток отменённых пакетов.
- `check-revenue.ts`, `check-revenue-parity.ts`: две реализации отчётов против SQL. Период зашит как 01.09.2025–31.08.2026, поэтому изменения нового учебного года ими автоматически не покрываются.
- `check-ledger-core.ts`, `check-money-cases.ts`, `check-wallet-transfer.ts`, `check-group-relink.ts`, `check-payment-create.ts`, `check-attendance-delete.ts`: сценарные проверки с созданием данных и откатом транзакции; это не read-only сверки. Они не доказывают безопасность параллельных транзакций.
- Исторические `backfill-*` и адресные `fix-*` не являются частью обычной работы ядра. В частности, `fix-split-instalment-pricing.ts` напрямую меняет старые строки журнала. Не использовать такие скрипты как образец новых команд и не перезапускать старые бэкфиллы на современной схеме.

## Что подтверждено на локальной базе

Организация «А Класс» — id 3. Все диагностические SQL выполнялись в `BEGIN READ ONLY` с откатом. Три существующие сверки запускались с `PGOPTIONS=-c default_transaction_read_only=on`.

- 222 активных и 23 архивных кошелька. В архиве школы нет положительных остатков, но активная группа №211 ученика №712 привязана к архивному кошельку №38.
- У действующей «Субботней геометрии» №330 — 24 активные записи; 13 используют общий кошелёк с активной математикой. Например, ученик №688: кошелёк №328 «Математика 7 класс», на него также назначены геометрия №330 и старая геометрия №114. В №330 уже есть 7 оплаченных посещений. Общий кошелёк законен технически; без таблицы школы нельзя утверждать, какие из 13 назначений ошибочны и каков правильный остаток.
- 44 записи пакетов на 36 активных кошельках подпадают под legacy-запрет: **17 пакетов уроков на 16 кошельках**, а также **27 денежных записей на 27 кошельках**; множества кошельков пересекаются. Это разные категории, их нельзя показывать одинаковыми редактируемыми абонементами.
- Отказ воспроизведён вызовом настоящей `planPackageCorrection` на данных пакета №2843, кошелёк №9 «Геометрия электив 8–9 классы»: `lessonCount=1`, `remaining=1`, `price=0`, `unitPrice=812`, счёта нет. Попытка добавить урок возвращает «Пакет перенесён из старой системы — его деньги учтены в другой записи».
- Точной фразы «нельзя изменить баланс, так как это повлияет на отчётность» в текущем коде нет. Форма содержит предупреждение «Правка меняет финансовые отчёты»; блокировки задаёт функция расчёта. Причину конкретной попытки менеджера без её входных данных установить нельзя.
- У школы 53 занятия ожидают оплаты. Это существенно для понимания итогового остатка после исправления.
- По всей локальной базе `check-ledger.ts` прошёл: 26 192 строки журнала, 1 486 кошельков, 3 611 пакетов, расхождений основных инвариантов нет. Сумма выручки журнала и посещений совпала. `check-package-statuses.ts` прошёл.
- `check-wallet-balance.ts` прошёл основные assert, но вывел 197 диагностических расхождений формулы размера пакета, включая 80 отменённых пакетов; 31 активная запись относится к «А-классу». Не объявлять их автоматически ошибками баланса или исправлять по этой формуле.
- У «Алгоритмики» три архивных кошелька содержат суммарно четыре урока. Полное скрытие архива без подготовки лишит пользователей доступа к переносу этих остатков.
- Дополнительная проверка возвратов: у 88 архивных кошельков «Алгоритмики» и 12 «А-класса» есть активные пакеты с существующими невозвращёнными списаниями. Даже при нулевом остатке отмена старого посещения может вернуть в них урок. Это не текущий положительный баланс, но обязательный сценарий новой архивации.

## Подход

Рекомендуется расширить существующую модель и команды. Альтернатива — отдельные подсистемы денежных обязательств и прав на занятия с новым журналом — потребует миграции CRM, отчётов и всей истории. Для текущего запроса это несоразмерно. Простое включение флага и снятие запретов не решает legacy-оценку, архив и конкурентные изменения.

Сохранить инварианты: `Σ WalletEntry.quantity по кошельку = lessonsBalance = Σ remaining ACTIVE-пакетов`; для выданных/отменённых пакетов `Σ quantity по пакету = remaining`; признанная выручка журнала согласована с посещениями. Нельзя назначать только `Wallet.lessonsBalance`.

### Привязка и перепривязка

Одна команда принимает `studentId, groupId, fromWalletId|null, toWalletId, mode, comment`.

- `KEEP_PAID`: меняет связь, оплаченные посещения/пакеты/цены остаются на месте. **Все ещё неоплаченные подходящие занятия**, включая старые, начинают погашаться новым кошельком. Это режим «Без пересчёта оплаченных», а не календарная привязка «с даты»; историю назначений по датам не вводим.
- `REPRICE_HISTORY`: сохраняет нынешнюю семантику `relinkGroupTx`, включая отработки и исключения для нулевых закрытий, старых долгов и отменённых пакетов. Оплаченные новым кошельком строки повторно не списываются.
- В обоих режимах перенос пакетов — отдельный явно выбранный состав операции, не автоматическое последствие смены группы. При общей команде сначала пакеты, потом группы.
- Показывать источник, получателя, режим, сколько занятий затронется, какие пропускаются и почему, остатки до/после и изменение выручки по месяцам.
- Доступ из карточки ученика/его группы, включая исторические записи и связь с архивным источником до миграции. Привязка без прежнего кошелька — та же операция с `fromWalletId=null`.
- Записывать событие связи даже без денежных движений; существующая история поддерживает `keepZero`.

### Коррекция остатка пакета

Два явных сценария: «Исправить продажу» (существующие поля суммы/количества) и «Установить остаток пакета» (ввод `targetRemaining ≥ 0`). Оба вызывают общий расчёт и исполнение.

Для второго сценария `newLessonCount = oldLessonCount + targetRemaining − oldRemaining`. Показывать «было выдано / списано / осталось», новое количество, новую цену урока и общий баланс кошелька. Если исторические данные дают некорректное новое количество, вернуть объяснение с конкретным пакетом, а не запрет из-за отчётности.

Сохраняется действующий защитный предел 500 занятий: остаток и получившийся размер — целые числа от 0 до 500. Расчётная стоимость — целое число от 0 до 2 147 483 647 ₽ (диапазон поля `Int`); причина — от 3 до 500 символов после trim. Эти пределы проверяются и в UI, и на сервере.

Основа оценки:

- У обычной продажи — `Package.price`; сумма CRM по-прежнему защищена. Изменение количества разрешено, даже если сумма пришла из CRM.
- У legacy-пакета уроков без счёта — обязательная введённая менеджером `pricingAmount` (целые рубли, ≥0). Сохранить новым nullable-полем `Package.pricingAmount`; это **расчётная стоимость**, не поступление. При следующих правках предлагать сохранённую величину. Не менять `Package.price`, `Payment.price`, «Оплачено до перехода» и старые денежные счётчики на её размер.
- Денежные записи перехода без уроков не являются пакетами для установки остатка. Показать их отдельно как историю денег; не конвертировать их в занятия этой формой. Классификацию строить по структуре и сохраняемым данным, не по свободному названию продукта. Неоднозначные старые записи включить в отчёт подготовки.
- Подарок определяется по структурированному событию выдачи `LESSONS_GIFTED` с id пакета, а не по названию или нулевой цене. Он сохраняет нулевую оценку. Остальные пакеты уроков без счёта, включая нулевую историческую оценку, требуют вводимой менеджером стоимости. Пакет без счёта с собственной ненулевой `price` тоже не меняет поступление: новая `pricingAmount` влияет только на оценку занятий. Новый подарок этим изменением не вводится.

Новая цена `floor(pricingBasis / newLessonCount)`. Если после снятия всего неиспользованного остатка новый размер равен 0, цена равна 0, поступления сохраняются, пакет не участвует в списании. Сохранённая расчётная стоимость позволяет впоследствии восстановить уроки без потери основания оценки. `CANCELLED` и `PENDING` этим действием не исправляются: у них иной жизненный цикл.

После коррекции выполняется штатное погашение очереди кошелька, затем возвращается фактический результат. Отображать отдельно установленный остаток пакета, планируемые списания, итоговые остатки пакета и кошелька. Даже уменьшение/правка цены может запускать погашение при наличии доступного остатка и ожидающих занятий; это должно совпадать в preview и commit.

Прошлые оплаченные занятия выбранного пакета переоцениваются; чужие уже оплаченные пакеты не перераспределяются. Переоценка — новые встречные записи на дне занятия; причина, автор, исходная и новая оценка сохраняются.

### Архив

Полное скрытие применяется к карточке ученика, селекторам и кабинету родителя, включая нынешний блок архивных курсов. Скрытие сущности не означает удаление оплаты/посещения из финансовой истории и отчётов.

Перед включением фильтра разобрать архив с остатками, ожидающими оплатами, активными связями и будущими явными назначениями `Attendance.walletId`: явная карта переноса на активные кошельки того же ученика, без догадки по названию курса. Подготовительный скрипт по умолчанию только показывает план; применение идемпотентно через ядро. Архив не возвращать автоматически в активный статус.

Новая архивация атомарно отказывает, если остаются уроки, `PENDING`-пакеты, активные назначения групп, ожидающие занятия или будущие явно назначенные посещения. Непроведённые занятия по завершённым группам тоже проверять по фактическим строкам, не только статусу группы.

**Возврат после архивации:** дополнительный блокирующий признак — активный пакет с невозвращёнными списаниями, даже при остатке 0. До архивации такой пакет целиком переносится в явно выбранный активный кошелёк того же ученика. Нулевой перенос не меняет прошлые посещения и цены; последующий штатный `unchargeAttendanceTx` возвращает урок текущему владельцу пакета. Тот же порядок повторяется, если получатель впоследствии архивируется. В диалоге архивации нужен доступ к переносу таких исчерпанных пакетов, которые обычный список переноса сейчас скрывает. Кошелёк-получатель нельзя выбирать по догадке; при отсутствии подходящего пользователь создаёт его явно.

Это предложение автора для сохранения возвратов, а не отдельное согласованное бизнес-решение. Подготовительный аудит включает такие пакеты и в уже существующем архиве; приведённые выше три положительных остатка не исчерпывают объём подготовки. Завершённые связи, отменённые пакеты и денежные записи без возможности возврата уроков остаются на архиве. Новые списания из архива запрещаются после подготовки; законный откат отменённого/старого беспакетного списания по-прежнему может записать нейтральную пару в его истории без появления остатка.

### Целостность и UX

- Все изменения выполняются в одной транзакции. Нужен общий порядок блокировок: сначала участвующие ученики по id, затем денежные сущности; для общего счёта учесть всех затрагиваемых учеников. Проверять состояние после захвата, включая старую посещаемость.
- Нынешняя перепривязка прямо документирует гонку с отметкой урока. У списания есть отдельное чтение положительного остатка и безусловное уменьшение; конкурентные сценарии требуют отдельных проверок, последовательные тесты их не покрывают.
- Preview переноса сейчас исполняет команду с откатом, кратко блокирует строки и не гарантирует совпадение при изменениях между preview и сохранением. Сохранить единый расчёт, добавить отпечаток исходного состояния и проверку под блокировкой. Изменился снимок — обновить preview, не применять невидимые последствия. Нельзя сохранять при загрузке/ошибке/устаревшем preview.
- Повтор одной отправки не должен применять коррекцию дважды. Предлагается технический `FinancialOperation` с уникальным `(organizationId, requestId)`, хешем запроса и результатом; деньги остаются в существующем журнале. Уже завершённую операцию искать до проверки отпечатка текущего состояния: повтор возвращает сохранённый результат, хотя состояние после первого сохранения уже другое. UUID операции связывает записи истории. Поля результата возвращать после фактического погашения.
- Серверные права и tenant/student-проверки нужны у всех затрагиваемых команд. `createWallet`, `renameWallet`, `archiveWallet` сейчас используют только `authAction`; новый UI не заменяет серверную проверку прав.
- После изменения инвалидировать кошельки, ученика, пакеты, неоплаченные занятия, историю, посещаемость и затронутые финансовые отчёты. Сейчас инвалидация неполная.

## Границы и критерии приёмки

Не меняем правила бесплатных пробных/отработок, не вводим возвраты денег, рассрочки, подарки, произвольные межученические переводы или новую систему финансовой отчётности. Сверка Google-таблицы и выбор правильных кошельков для конкретных учеников требуют данных школы и не делаются автоматически.

Менеджер способен исправить обычный и legacy-пакет с понятным результатом; ни предупреждение об отчётах, ни отсутствие счёта у пакета уроков сами по себе не блокируют операцию. Оба режима связи предсказуемы. Архив не виден, но деньги и история не потеряны. Повтор/конкуренция не создают двойного списания. Основные сверки до и после проходят, а изменение прошлой выручки соответствует подтверждённому preview по месяцам.

Статус проверки документа: самостоятельная проверка по коду и данным выполнена. Независимый builder check был запрошен, но завершился ошибкой лимита использования до выдачи замечаний; независимая проверка не состоялась.
