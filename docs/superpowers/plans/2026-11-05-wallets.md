# Кошельки — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Этот документ подготовлен для рассмотрения; текущая задача не включает реализацию.

**Goal:** Дать менеджеру привязку/перепривязку групп с выбором режима, коррекцию остатка обычных и старых пакетов и убрать архивные кошельки из интерфейса.

**Architecture:** Расширить существующие `ledger`, `transfer`, `correction`, сохранив общий журнал и расчёт отчётов. Отделить расчётную стоимость legacy-пакета от поступления. До скрытия архива устранить недоступные остатки и действующие назначения.

**Tech Stack:** Next.js 16 / React 19, TypeScript, Prisma 7 / PostgreSQL, next-safe-action, Zod, TanStack Query. Сценарные проверки — существующие `tsx`-скрипты.

**Spec:** [Анализ и проект изменений](../specs/2026-11-05-wallets-design.md).

## Global Constraints

- UI и сообщения на русском; дата операции — бизнес-день часового пояса школы.
- Деньги и посещения меняются только атомарными командами ядра. Старые строки журнала не переписывать.
- Привязка относится к ученику в группе; межученический перенос запрещён.
- Пересчёт прошлого разрешён пользователем; влияние показывается до сохранения.
- Остаток вводится до погашения ожидающих занятий. `pricingAmount` старого пакета вводит менеджер; это не поступление.
- Остаток/получившийся размер: целые 0–500; расчётная стоимость: целые 0–2 147 483 647 ₽; причина после trim: 3–500 символов.
- Архив полностью скрыт; без кнопки раскрытия. История и финансовые отчёты его не теряют.
- Не запускать старые бэкфиллы и адресные исправления как миграцию этой задачи.
- Новые поля добавляются миграцией; `prisma format` не запускать. Проверка схемы — `prisma validate`.

## Review Focus

- Пакет без счёта: изменение расчётной стоимости не меняет поступления и не дублирует денежный пакет перехода — задача 2.
- Установка 0 у полностью неиспользованного пакета и последующее восстановление сохраняют основание оценки — задача 2.
- Историческая отработка, бесплатное пробное и отменённый пакет при двух режимах связи — задача 3.
- Скрытый архив с живой связью, положительным остатком или будущим явным посещением не теряет обязательства — задача 4.
- Одновременные отметка/перенос/коррекция и повтор после тайм-аута не создают лишних движений — задачи 1 и 5.

## Task 2: Установка остатка и оценка старых пакетов

**Files:** `packages/db/prisma/schema/finance.prisma`, новая миграция; `finances/correction.ts`, `correction.server.ts`, `ledger.server.ts`; `wallets/schemas.ts`, `actions.ts`; новый `check-package-correction.ts`, существующий `check-ledger-core.ts`.

**Interfaces:** дополнить факты пакета `pricingAmount:number|null` и явной способностью коррекции (`SALE`, `LEGACY_LESSONS`, `GIFT`, `MONEY_ONLY`, `UNSUPPORTED`). Новая команда `setPackageRemainingTx(tx, {packageId, targetRemaining, pricingAmount?, comment, organizationId, actorUserId, effectiveAt}): Promise<CorrectionReport>`. `CorrectionReport` содержит остатки выбранного пакета/кошелька до, после установки и после погашения, число погашенных занятий, цену урока и помесячное влияние. Внешний экшен использует контекст задачи 1.

- [ ] Зафиксировать тесты обычного пакета: 8 занятий за 8 000 ₽, 3 списаны, остаток 5; установка 7 даёт размер 10 и цену 800 ₽, переоценивает 3 занятия на −600 ₽. При двух ожидающих занятиях и единственном пакете итоговый остаток 5, цена каждого нового списания 800 ₽.
- [ ] Зафиксировать legacy-сценарий на обезличенной копии формы №2843: остаток 1, счёта нет; менеджер задаёт стоимость 1 000 ₽ и остаток 2 → цена 500 ₽. `Package.price`, все `Payment.price` и денежные записи перехода остаются прежними. Отсутствие расчётной стоимости даёт ошибку поля; число нельзя угадывать.
- [ ] Добавить проверки CRM (количество разрешено, сумма защищена), подарочного нуля с подтверждённым событием `LESSONS_GIFTED`, legacy с прежней нулевой оценкой, денежной записи перехода, частично потраченного пакета, нулевого размера, восстановления из нуля, повторной оценки после округления, перенесённого пакета и отката переоценённого посещения. У старого пакета без счёта с ненулевой `price` новая оценка тоже не меняет `price`.
- [ ] Добавить nullable `Package.pricingAmount` без массового автоматического заполнения. Показать нераспознанные старые структуры в диагностике; не классифицировать их по названию. Сохранить стоимость после уменьшения размера до нуля.
- [ ] Общий план коррекции вычисляет новый размер из заданного остатка и текущих фактов. Исполнение меняет пакет, пишет `ADJUSTMENT` и пары переоценки, затем гасит очередь кошелька. Текущий `correctPackageTx` использует те же правила и не обнуляет legacy-оценку.
- [ ] Превью выполнить тем же исполнителем в транзакции с откатом; возвращать полный результат и отпечаток, а не клиентскую оценку `Math.min(unpaid, balance)`. Следить за ограничением времени транзакции и размером очереди.
- [ ] Запустить `check-package-correction.ts` и `check-ledger-core.ts`; проверить сохранение суммы журнала по пакету/кошельку и согласованность помесячной выручки.

Результат: пользователь исправляет остаток, а фактические поступления и расчётная стоимость не смешиваются.
